# 클라우드 보안 점검을 설계와 용량산정에 연결하기

2024.06 [클라우드 취약점 점검 가이드](../sources/pdf-1e5aa3fe692c.md)는 클라우드 시스템의 설정 취약점(CCE) 점검을 돕는 자료다. PDF p.7은 진단항목·설명·기준·방법·조치방법으로 구성된 39종 기술 가이드를 소개한다. PDF p.8은 기능·버전·운영상황에 따라 방법과 판단기준이 달라질 수 있다고 명시한다. 아래 연결 방법과 웹 데이터 구조는 이 프로젝트의 설계 제안이다.

## 자산에 맞는 항목부터 찾는다

자산 종류, 제품·버전, 역할, 운영 주체를 먼저 기록한다. Kubernetes의 관리 영역과 워커, 호스트와 컨테이너, 데이터베이스와 저장장치를 구분한다. 관리형 서비스에서는 사용자가 확인할 수 있는 설정 범위도 함께 남긴다. 가이드에 해당 기술이 있다는 이유만으로 모든 항목을 적용하거나 양호로 판정하지 않는다.

| --- | --- | --- |
| Docker | p.511 표26, 32항목 | 호스트·데몬·파일·이미지·런타임 항목을 해당 자산에 연결 |
| Kubernetes 관리 영역 | p.549 표27, 17항목 | API 접근·인증·권한, 로그, etcd, 파드 권한, 파일, 패치 검토 |

## 용량산정에 필요한 질문으로 연결한다

| 원문 항목 | 산정 전에 추가로 확인할 내용: 프로젝트 제안 | 계산 시 처리 |
| --- | --- | --- |
| KVM 로그 관리·백업, p.18 | 로그 발생량, 보관 기간, 백업 주기·복사본, 전송 구간 | 확인한 값을 스토리지·네트워크 입력 근거로 연결. 같은 데이터를 이중 계상하지 않음 |
| API Server 로그 관리, p.557 | 수집 대상, 피크 발생량, 로테이션, 중앙 수집·보관 위치 | 애플리케이션 데이터와 로그의 산정 범위를 구분 |
| etcd 암호화·TLS, p.560~561 | 적용 기능·구성, 성능 시험 조건, 실제 부하 영향 | 측정 없이 CPU나 지연 보정계수를 만들지 않음 |
| Docker PIDs 제한, p.543 | 업무 프로세스 수, 피크·장애 시 동작, 자원 제한 조건 | 프로세스 수 제한을 CPU·메모리 요구량으로 환산하지 않음 |
| 네트워크 관리 접속·ACL, p.699 | 관리망과 서비스망, 수집·백업 경로 | 트래픽 범위와 장비 성능 시험 구성을 명시 |

이 가이드는 새로운 용량 계산식의 출처가 아니다. 기존 21식과 보정계수는 그대로 두고, 필요한 가정·설계 확인 질문의 출처로 연결한다. 로그 보관 등의 별도 계산을 자동화하려면 입력·단위·중복 처리 계약을 먼저 작성해야 한다.

## 웹과 에이전트에서 기록할 상태

후속 점검표는 `자산 → 제품·버전 → 출처·페이지·항목명 → 적용 여부·이유 → 점검 결과 → 증적·점검일·확인자`를 연결한다. 원문에 없는 항목 ID는 프로젝트 내부 ID라고 표시한다.

- 적용 여부: 미확인 / 적용 / 제외 사유 검토 완료.
- 점검 상태: 미점검 / 증적 검토 중 / 양호 / 취약 / 판정 보류.
- 개선 조치와 재점검은 별도 기록으로 남긴다. 조치안을 작성한 것만으로 점검 상태를 양호로 바꾸지 않는다.

두 상태 축을 분리하면 자료 부족을 취약 또는 양호로 오인하지 않는다. LLM은 해당 항목 찾기·설명·추가 질문을 담당하며, 문서에 있는 삭제·방화벽·재시작 명령을 자동 실행하지 않는다. 최초 웹 버전에서는 Wiki와 원문을 열람하고, 실제 점검표 편집·증적 관리는 후속 단계로 둔다.

## 적용 범위와 확인 한계

39개 장의 위치와 주요 체크리스트를 정리했고 전체 텍스트를 페이지별로 추출했다. 766페이지의 모든 명령·화면·제품 버전 적합성을 검증한 것은 아니다. 원문 예제와 명령 표기는 해당 제품의 공식 문서·대상 버전과 대조한 뒤 사용해야 한다. 현행 CSAP·ISMS-P 적합성이나 실제 시스템의 보안 상태는 이번 Wiki 등록으로 판정하지 않는다.
