# 프로젝트 중심 On-Prem·AWS 설계

2026-09-28 · P2.2 사용자 추가 요구사항. 프로젝트 계층·자산·마이그레이션·사용률 최적화의 구현 계약이다.

## 사용자 흐름

Capacity Agent의 최상위는 프로젝트 목록이다. 프로젝트를 선택해야 해당 프로젝트의 On-Prem/AWS 작업공간에 들어간다. 프로젝트마다 자산·실사용 최적화·TTA 계산·AWS 초안·저장 이전안·산정서를 분리한다. 프로젝트 전환은 데이터 교체/삭제가 아니며, 기존 단일 브라우저 프로젝트는 첫 프로젝트로 보존한다. JSON 가져오기는 별도 프로젝트로 추가하는 것을 기본으로 한다. 현재 단계는 이 브라우저의 로컬 프로젝트이며 서버 협업/계정 권한은 후속 범위다.

1. On-Prem 첫 화면은 자산 목록이다. 검색·필터·페이지·할당량/사용률·측정 상태를 함께 본다.
2. 이름을 누르면 별도 자산 상세로 이동한다. 현재 사양, 측정 사용량, 견적 검토 정보와 근거를 확인하고 명시적인 수정 버튼으로 편집한다.
3. 해당 자산의 실사용량과 성장·목표 활용률·디스크 여유율을 입력해 최적화 시나리오를 계산한다. 원본 할당량과 필요 용량의 차이를 비교하고 이름을 붙여 저장한다.
4. On-Prem 시나리오 목록에서 같은 자산·같은 계산 모델의 두 안을 비교하고 산정서를 내보낸다. TTA/네트워크 기반 신규 업무 규모 산정은 별도 모델로 구분하고 업무/대상 정보를 기록한다.
5. AWS에서는 자산별 조건·후보 설정 후 여러 행을 선택한다. 검토 창에서 각 자산의 최신 상태·후보·부분 비용을 확인하고 한 번에 이전안 목록에 저장한다.

## 화면 계층

```text
Capacity Agent
└─ 프로젝트 목록 → 프로젝트 선택
   ├─ 통합 대시보드
   ├─ On-Prem
   │  ├─ 서버 자산 → 자산 상세 → 수정 / 실사용 최적화
   │  ├─ 용량산정 (TTA·네트워크)
   │  └─ 산정 시나리오 → 비교 / 산정서
   ├─ AWS
   │  ├─ AWS 마이그레이션 → 원본 자산별 조건·후보 → 선택 일괄 검토 저장
   │  ├─ 이전안·시나리오 → 복제 / 비교 / 산정서
   │  ├─ AWS 자산 → 현재 EC2·gp3 사양 상세
   │  ├─ 최적화 → 자산별 사용률 기반 제안
   │  └─ 최적화 시나리오 → 비교 / 산정서
   └─ 공통: 산정서 / 산정 Wiki / 벤치마크 참고
```

상위 On-Prem/AWS 탭을 제거하고 두 환경을 좌측 탐색에 동시에 표시한다. 상단 경로는 프로젝트·환경·목록·자산을 구분한다. Cloudscape의 [서비스 탐색 패턴](https://cloudscape.design/patterns/general/service-navigation/)을 참고했다. 통합 대시보드는 두 환경의 자산 수, 측정 근거 준비, 저장한 이전안과 최적화안, 최근 저장 항목을 보여준다. 운영 자산과 계획 후보를 합산하지 않는다.

주소는 `#project/{projectId}/{section}`이며 자산 상세는 `assets/{assetId}`, 마이그레이션 상세는 `migrate/{assetId}`, AWS 최적화 상세는 `aws-optimize/{assetId}`다. 다른 프로젝트의 자산 ID는 현재 프로젝트에서 찾을 수 없는 상태로 표시한다. 이전 단일 프로젝트 주소는 첫 로컬 프로젝트의 경로로 연결한다.

## 프로젝트 저장

IndexedDB `capacity-agent.projects.v2`의 `projects` 저장소에 프로젝트별 레코드·revision·수정 시각을 보관한다. 생성과 가져오기는 고유한 프로젝트 ID를 사용하며 기존 프로젝트를 덮어쓰지 않는다. 기존 `capacity-agent.workspace.v1` 바이트는 삭제하지 않고 최초 1회 트랜잭션으로 옮긴다. 구버전 탭은 새로고침해야 하며, 구버전 탭에서 이후 편집한 값은 자동 병합하지 않는다.

쓰기 요청은 순서대로 처리하고 IndexedDB readwrite 트랜잭션 안에서 예상 revision을 비교한다. 다른 탭이 먼저 저장했다면 해당 프로젝트의 자동 저장을 중지하고 편집본 JSON 백업·새로고침을 안내한다. 다른 프로젝트의 저장은 계속 가능하다. 공동 편집이나 자동 병합을 제공하지 않는다. 저장 진행 중 탭 닫기에는 브라우저 이탈 보호를 적용한다.

프로젝트 JSON은 20MB, 각 환경의 자산은 200개, 마이그레이션안과 최적화안은 각각 200개, TTA·네트워크 계산 묶음은 30개까지다. CSV는 1MB, 개별 API 입력은 2MB다. 저장 결과는 선택 후보만 보관하며 JSON 가져오기는 모든 결과를 서버 엔진으로 재계산한 다음 새 프로젝트로 원자적으로 추가한다.

## 할당과 사용량

- CPU: 할당 논리 CPU와 피크 사용률(%). 동일 시스템 기준 필요 논리 CPU와 AWS 상대성능 가정을 구분한다.
- 메모리: 할당 GiB와 피크 사용 GiB 또는 피크 사용률(%). 입력 방식을 명시하고 두 수치가 동시에 서로 다른 기준으로 적용되지 않게 한다.
- 디스크: 논리 할당 GiB와 실제 사용 GiB 또는 사용률(%). 기존 `disk_gib`는 실제 사용량이라는 의미를 보존한다. 원시 RAID 용량을 입력하지 않는다.
- 사용률로 입력하면 사용량 = 할당량 × 사용률 / 100을 계산 엔진이 정확한 유리수로 산출한다. 미입력은 0으로 채우지 않는다. 사용량이 할당량보다 크면 측정 범위를 확인하도록 거부한다.
- 측정일·근거와 성장/목표 사용률 등 설계 가정을 분리한다. 기존 프로젝트는 기존 사용 GiB 방식으로 읽는다.

## 계산과 시나리오

실사용 최적화는 현재 서버와 같은 논리 CPU 성능을 전제하는 계획값이다. CPU·메모리는 성장과 목표 활용률을 적용하고, 디스크는 별도 성장과 여유 공간을 적용한다. 필요한 정수 자원은 보수적으로 올림하고 수식·원값·적용 가정을 남긴다. 성능 개선이나 실제 자원 축소 가능성을 보증하지 않는다.

TTA tpmC/max-jOPS를 코어로 변환하거나 실사용 최적화 수치와 비교하지 않는다. 시나리오 비교는 동일 자산·모델·버전끼리만 허용한다. 저장 결과는 원본과 조건의 스냅샷이며 원본 변경과 독립적으로 유지한다. 가져오기는 입력부터 재계산한다.

일괄 이전안 저장은 최신 계산과 선택 후보가 있는 자산만 검토할 수 있다. 저장 전 누락·재산정 대상·프로젝트 한도와 동일 안 저장 여부를 보여준다. 성공 시 하나의 원자적 상태 변경으로 저장하고 이전안 목록으로 이동한다. 계산만으로 검토 완료 표시를 만들지 않는다.

## AWS 사용률 최적화

현재 운영 EC2는 `awsAssets`, On-Prem 원본은 `assets`에 분리한다. `POST /api/optimize` 요청의 `environment`는 `onprem` 또는 `aws`이며 결과 모델은 `utilization-planning-1.0.0`이다. AWS는 현재 인스턴스 유형과 할당 CPU·메모리·아키텍처 일치를 검사한다. 사양 변경 후보는 서울 카탈로그의 동일 아키텍처로 제한하며 논리 CPU 상대성능 1 가정을 명시한다. EC2 1대·gp3 1개 범위이며 Auto Scaling·RDS·다중 볼륨 최적화는 후속이다.

동일 월 사용시간과 Linux/Windows On-Demand 가격으로 현재 EC2+현재 gp3와 제안 EC2+제안 gp3를 비교한다. 현재 gp3 할당량·프로비저닝 IOPS·처리량이 모두 있어야 비용 차이를 계산한다. 누락은 0원 절감으로 표시하지 않는다. 차이 = 현재 − 제안이며 음수는 비용 증가다. 후보가 없으면 저장하지 않는다.

[Compute Optimizer의 사용률·headroom·측정 기간 지침](https://docs.aws.amazon.com/compute-optimizer/latest/ug/rightsizing-preferences.html)과 [측정 지표 설명](https://docs.aws.amazon.com/compute-optimizer/latest/ug/metrics.html)을 참고한다(2026-09-28 확인). 이 제품은 시계열을 수집하거나 AWS Compute Optimizer API/ML 알고리즘을 실행하지 않는다. 피크·기간·백분위는 사용자가 근거에 기록한다. [EBS 공식 변경 제약](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-modify-volume.html)에 따라 축소 제안은 새 볼륨으로 이동·검증하는 별도 작업이며 기존 볼륨 직접 축소가 아니다.

## 구현 책임

- `projectStore.ts`: 트랜잭션·revision·기존 저장값 전환·가져오기 재계산.
- `ProjectHub.tsx`, `App.tsx`, `Dashboard.tsx`: 프로젝트 선택·경로·공통 레이아웃·통합 현황.
- `Inventory.tsx`, `AssetEditor.tsx`: 환경별 자산 목록·CSV·검증·편집.
- `Optimization.tsx`, `OptimizationScenarios.tsx`: 상세·가정·제안·비교. `Review.tsx`에서 공통 산정서 출력.
- `capacity_web/migration.py`: 사용량/사용률 해석과 마이그레이션1.1.0. 기존 산술 모델은 유지한다.
- `capacity_web/optimization.py`: 동일 성능 가정의 요구량·정수 올림·AWS 현재/제안 비용 비교.

## 완료 증거

- 독립 산술로 사용률→GiB·성장/목표 활용률·디스크 여유·경계값·기존 프로젝트 호환 검증.
- 자산 목록→상세→수정→최적화→저장→동일 자산 비교→산정서·JSON 재계산을 실제 브라우저에서 확인.
- AWS 선택 여러 건의 검토 저장 성공과 미산정/오래된 초안·초과 한도의 원자적 거부 확인.
- 모바일·키보드·접근성, 늦은 응답·취소·새로고침 저장, 기존21식·AWS golden 회귀 유지.
- 문서·public commit/push·GitHub CI·실행 중 대시보드로 사용자에게 인계.
