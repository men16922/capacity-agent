# Wiki에서 용량산정 웹과 에이전트로

2026-09-28 · 제품 기획. 현재 구현과 후속 계획을 구분한다.

## 제품 목표와 대상

웹에서 **근거를 추적할 수 있는 용량산정서**를 만들 수 있다. 요구사항을 구조화한 입력으로 바꾸고 버전이 지정된 계산 엔진이 수치를 계산하며, LLM은 질문·검색·설명을 담당하는 구조가 적합하다.

현재 자료는 일반 정보시스템 인프라의 서버·스토리지·네트워크 및 구축·보안 문서다. GPU나 LLM 서빙 전용 용량산정에는 별도 지식과 모델이 필요하다.

추가된 [TTA·AWS 계산 워크북](../wiki/sources/xlsx-d6bfd84a3ce8.md)은 입력·가정·결과 화면과 실측 기반 확장 기능의 참고다. TTA 표준 식, 워크북의 AWS 산정 가정, 현행 AWS 사양 검증을 분리한다. 워크북 수식이나 PASS 저장값을 검증된 웹 엔진으로 간주하지 않는다.

## 핵심 제품 흐름

상위 메뉴는 **On-Prem / AWS**, 핵심 기능은 **On-Prem 사양 → AWS 마이그레이션**이다. 2026-09-27 사용자 지시에 따라 AWS 실측·직접 경로, EC2/gp3 후보와 비용을 P2로 올렸다. [웹 화면 계획](WEB_PLAN.md)과 [마이그레이션 설계](MIGRATION_DESIGN.md)에 입력·단위·화면·완료 조건을 정리했다.

## 수십 개 자산을 검토하는 핵심 사용 사례

TA가 CSV로 최대 200개 서버를 등록하고 AWS 이전 대상 목록에서 검색·필터·선택한다. 공통 조건을 적용한 뒤 일괄 산정하고, 각 자산의 상세에서 원본·이전 조건·후보·근거를 검토한다. 담당자가 확인한 안만 별도로 저장하여 비교·산정서로 전달한다. 산정 오류 한 건이 전체 작업을 막지 않아야 하고, 변경 전 금액이 최신 합계에 섞이지 않아야 한다.

공통 분류는 자산 유형·운영 환경·OS/제품 버전·애플리케이션 연결·라이선스·의존성·복구 요구다. 특정 기업/클라우드 사업자 이름을 기본 항목으로 고정하지 않는다. [견적 입력 항목과 공식 근거](ESTIMATION_INPUTS.md)를 데이터 사전으로 사용한다.

현재 결과물은 사양을 충족하는 후보 및 EC2+EBS 부분 비용이다. 최종 견적 승인, 실제 AWS 이전, 자동 자산 통합, 전체 TCO 산정은 제공하지 않는다.

## 에이전트 확장 시 사용자 흐름

1. 프로젝트와 산정 시점, 서비스 형태, 서버 역할을 정한다.
2. 직접 양식을 입력하거나 업무 설명을 붙여 넣는다.
3. 에이전트가 동시 사용자 정의, 피크 부하, 데이터 보관, 이중화 등의 빠진 항목을 질문한다.
4. 입력값·단위·가정·보정계수·근거를 한 화면에서 검토한다.
5. 계산 엔진이 결과와 중간값을 반환한다.
6. 기준·성장·피크 시나리오를 비교하고 필요한 값을 수정한다.
7. 산정서, 입력 JSON, 요구사항 추적표를 내보낸다.
8. 후속 단계에서 사양서·구성 점검표·검수 증적을 연결한다.

초기 웹 계산기는 1·2·4·5·6·7을 LLM 없이도 제공한다. 모델 사용 가능 여부가 계산 기능을 막지 않도록 한다.

## 기능의 책임

| 영역 | 책임 | 근거·검증 |
| --- | --- | --- |
| Wiki | 원문 출처, 개념, 버전, 충돌 관리 | 해시·페이지·시트·셀·연결 |
| 입력 검증 | 자료형, 단위, 범위, 필수값, 조합 검사 | 스키마 및 경계 사례 |
| 계산 엔진 | CPU 지표·메모리·디스크·선택 네트워크 식 | Decimal 기반 기준값과 독립 회귀 검증 |
| 웹 | 양식, 가정 검토, 중간식, 시나리오 비교, 출력 | 실제 브라우저에서 입출력 확인 |
| LLM | 원문 해석, 누락 질문, 검색, 설명 초안 | 출처 인용, 미확인 입력 보존, 도구 호출 평가 |
| 장비 선정 | 실제 카탈로그·성능·가격·가용성 대조 | 근거 버전과 비교 가능성 확인 |

LLM이 작성한 숫자를 최종 산정값으로 저장하지 않는다. 도구 결과의 값·단위·규칙 버전은 변경 없이 사용하고, 서술만 덧붙인다. 장비 가격이 없으면 비용은 미산정으로 남긴다.

## 기술 구조 제안

계산 코어는 UI와 모델 SDK에서 분리한 순수 라이브러리로 만든다. 현재 Python의 Decimal 입력 파싱·정확한 유리수 연산·JSON 입출력으로 기준 엔진 1.0.0을 구현했다. 웹에서 같은 엔진을 호출하면 프런트엔드와 서버의 계산식 중복을 피할 수 있다. 웹 UI는 React·TypeScript·Cloudscape, HTTP 어댑터는 FastAPI로 구현한다. 모델 공급자·인증·호스팅은 후속 결정이다.

36개 출처 규모에서는 처음부터 벡터 DB를 운영할 필요는 없다. source ID·제목·주제·본문 검색과 원문 위치를 활용해 검색 품질을 먼저 평가한다. 표가 단절되는 청크 분할을 피하고 식·변수·단위·출처는 하나의 검색 단위로 유지한다. 하이브리드 검색이나 벡터 저장소는 평가에서 필요성이 확인될 때 추가한다.

에이전트 도구의 제안 계약:

벤치마크 탐색은 [공식 사이트 조사](../wiki/benchmarks.md)와 [링크 목록](../wiki/sources/external-links.json)을 바탕으로 추가한다. 결과 ID·버전·시험 구성·상태·확인일을 저장하고, 규칙으로 계산한 요구량과 측정된 후보 성능을 구분한다. SPC-1C 목록은 혼합 표시가 관찰되어 개별 보고서 검증 없는 자동 수입을 보류한다.

```text
search_knowledge(query, source_version?) -> cited_passages
validate_inputs(profile_id, inputs) -> missing_fields, errors, assumptions
calculate_capacity(profile_id, rule_version, confirmed_inputs) -> calculation_result
compare_scenarios(scenarios) -> result_differences
render_report(calculation_result) -> artifact
```

구매, 배포, 실제 서버 설정 변경은 이 에이전트의 초기 범위가 아니다. 원본 전체를 외부 모델에 보내는 방식도 아직 결정하지 않았다. 모델 연결 시 자료 처리 범위를 따로 정한다.

P0 Wiki·P1 계산 엔진·P2 On-Prem/AWS 대시보드를 구현했다. 추가 네트워크 가이드도 별도 프로파일로 구현했다. [요구사항별 검증](ENGINE_VERIFICATION.md)을 참고한다. HWP 표·내장 그림의 완전한 복제, LLM 연결·밤샘 루프 실행은 별도 단계다. 웹 완료 증적은 [웹 검증](WEB_VERIFICATION.md)에 기록한다.

## 먼저 확정할 설계 선택

첫 엔진은 TTA R3 본문과 두 네트워크 프로파일, 역할별 계산, 장비 모델을 특정하지 않는 출력을 제공한다. 코어·서버 대수, 물리 RAID 구성, 현대 미들웨어 메모리 실측, 비용·보안 적합성은 자료 보강이 필요한 후속 영역이다.
